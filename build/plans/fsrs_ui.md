# SkillTape — FSRS scheduling implementation plan

## Goal

Make the spaced-repetition engine visible and authoritative in the UI. Today the home screen is a manual topic grid; scheduling either isn't wired or isn't surfaced. After this work:

- Home shows what is actually due and offers a one-click entry into a review session.
- Drill grades items through FSRS and shows the four predicted intervals before you choose.
- Every review is logged so the FSRS optimizer can be run against real history later.
- Practice and Exam modes are untouched.

## Guardrails

- **One scheduler module.** All FSRS math lives behind a single service. No component, route, or query computes an interval itself.
- **Additive migrations only.** Existing quiz history, best scores, and item content must survive. No destructive column changes.
- **Feature-flagged.** Ship behind a settings toggle so the old home grid remains reachable until the new path is trusted.
- **Do not modify Practice or Exam grading.** They are batch-graded with free navigation; per-item ratings do not apply there.
- **Round every displayed number.** Intervals in days, stability to one decimal, retrievability as a whole percent.

---

## Phase 0 — Audit

Before writing anything, establish what exists.

1. Check whether `ts-fsrs` is already a dependency and what version.
2. Grep for existing FSRS usage: `fsrs`, `stability`, `difficulty`, `scheduled_days`, `due`, `retrievability`.
3. Read the SQLite schema. Identify the items table, the quiz/attempt tables, and how per-item results are currently persisted (if at all).
4. Identify the Drill component and its answer-submission handler.
5. Identify the home screen component that renders the topic grid.

**Output:** a short written summary of what is already wired, what is stubbed, and what is missing. Do not proceed until this is written down.

If FSRS state columns already exist and are being written, skip the schema work in Phase 1 and go straight to verifying correctness.

## Phase 1 — Data layer

### Item scheduling state

Add to the items table (or a sibling `item_schedule` table keyed by item id — prefer a sibling table if the items table is regenerated by Item Studio's dual-write):

| Column | Type | Notes |
|---|---|---|
| `due` | INTEGER | epoch ms, null until first review |
| `stability` | REAL | null until first review |
| `difficulty` | REAL | null until first review |
| `elapsed_days` | INTEGER | days since previous review at time of last review |
| `scheduled_days` | INTEGER | interval assigned at last review |
| `reps` | INTEGER | default 0 |
| `lapses` | INTEGER | default 0 |
| `state` | TEXT | `new` / `learning` / `review` / `relearning` |
| `last_review` | INTEGER | epoch ms, null until first review |

**Important:** if Item Studio writes items back to `.js` source files, scheduling state must NOT round-trip into those files. It is user progress, not content. Keep it in its own table and make sure the dual-write path ignores it.

### Review log

New append-only table:

| Column | Type |
|---|---|
| `id` | INTEGER PK |
| `item_id` | TEXT / INTEGER, FK to items |
| `rating` | INTEGER 1–4 |
| `state_before` | TEXT |
| `stability_before` | REAL |
| `difficulty_before` | REAL |
| `elapsed_days` | INTEGER |
| `scheduled_days` | INTEGER |
| `reviewed_at` | INTEGER epoch ms |
| `duration_ms` | INTEGER, nullable |
| `params_version` | TEXT |

`params_version` matters. When the optimizer produces custom weights, logs written under old weights need to be distinguishable.

Never update or delete rows here. Undo is implemented by writing a compensating action against the item state, not by mutating the log.

### Migration

Use whatever migration mechanism the project already has. If there is none, add a `schema_version` table and a numbered migration runner. Migrations must be idempotent and safe to run against an existing populated database.

**Verify:** run the migration against a copy of a real database. Confirm row counts on all pre-existing tables are unchanged and the app still boots.

## Phase 2 — Scheduler service

Create a single module, e.g. `src/main/scheduler/index.ts`. This is the only file that imports `ts-fsrs`.

### Public surface

```
initScheduler(settings)         // build FSRS instance from stored params
previewRatings(item, now)       // -> { again, hard, good, easy } each with card + interval
applyRating(itemId, rating, now, meta)  // persist state + write review log
getRetrievability(item, now)    // 0..1
undoLastReview(itemId)          // rollback via ts-fsrs, compensating write
resetItem(itemId)               // forget
getDueCounts(scope)             // { new, learning, due }
getDueQueue(scope, limit)       // ordered item ids
```

### Implementation notes

- `previewRatings` wraps a single `f.repeat(card, now)` call. That call already returns all four outcomes. Do not call it four times.
- Build the FSRS instance from `generatorParameters({ request_retention, maximum_interval, enable_fuzz })` read from settings. Rebuild it when settings change.
- Map between the DB row shape and the ts-fsrs `Card` shape in one place, both directions. Nothing outside this module should know the ts-fsrs field names.
- `applyRating` must be a single transaction: update item state and insert the review log together, or neither.
- Guard against double-submit. If a rating arrives for an item whose `last_review` is within a small window and the rating is identical, treat it as a no-op.

### Queue ordering

`getDueQueue` should return, in order:

1. Items in `learning` or `relearning` whose due time has passed.
2. Items in `review` whose due time has passed, oldest overdue first.
3. New items, capped by a configurable daily new limit.

Scope is a topic id, a set of topic ids, or all. Reuse whatever selection shape the Practice screen already uses so the two stay consistent.

**Verify:** write unit tests against the module with a fixed clock. Assert that four Good ratings produce a strictly increasing interval sequence, that a lapse reduces stability and increments `lapses`, and that changing desired retention changes the interval for the same card state.

## Phase 3 — Rating derivation

SkillTape auto-grades. There is no human choosing Again/Hard/Good/Easy, so the rating must be derived.

Start deliberately simple:

- Incorrect → `Again`
- Correct → `Good`

Put this in one function, `deriveRating(result)`, in the scheduler module. Do not scatter the logic.

Leave a documented extension point for later refinement using answer latency and format:

- Correct but slow relative to that item's rolling median → `Hard`
- Correct and fast on an item with high stability → `Easy`

Do not implement latency-based ratings in this pass. Capture `duration_ms` in the review log now so the data exists when you want to tune it.

For free-text formats graded by the local Ollama model, map the grader's verdict onto the same two-way split. If the grader emits a confidence or a partial score, threshold it — do not invent a four-way mapping from a score the model wasn't asked to produce.

## Phase 4 — Home screen due strip

Replace the current instruction line above the topic grid.

- Left: counts, formatted as `N due · N learning · N new`.
- Right: primary action button, labelled with the review count, e.g. `Start review (23)`.
- If nothing is due: show a quiet completion state and keep the button available as "Review ahead", which pulls the next-soonest items.

On each topic card, replace or supplement the `not attempted` line with a due count for that topic. Keep the existing best-score bar and dot strip — they are earned progress and shouldn't be removed.

The grid stays. Clicking a topic still works exactly as it does now. The strip adds a path, it does not replace one.

**Verify:** counts must match a direct SQL query against the same clock. Off-by-one on timezone boundaries is the likely bug — decide explicitly whether "due today" means "due before end of local day" and apply that rule in one place.

## Phase 5 — Drill integration

Drill is the only mode that gets FSRS ratings. One item at a time, graded immediately.

### Flow

1. Session starts from `getDueQueue`, not from a topic's full item list.
2. Item renders. User answers. Correctness is determined as it is today.
3. On reveal, call `previewRatings` and render the grade bar.
4. Auto-select the derived rating and apply it, but show all four intervals so the decision is legible.
5. Optional: allow manual override of the auto rating. If added, the manual choice wins and is what gets logged.

### Grade bar

Four buttons in a row. Each shows the rating label and the predicted interval underneath, formatted as `10m`, `3d`, `2mo`, `1.4y`. Colour by semantic role: danger, warning, success, accent. The auto-selected one gets an emphasized border.

This component is the point of the whole feature. It should be visible on every Drill item, not behind a toggle.

### Session end

Show a summary: items reviewed, again count, and when the next item comes due. Then return to home so the due counts visibly drop.

**Verify:** complete a session, close the app, reopen it, and confirm the state persisted and due counts updated.

## Phase 6 — Settings

Add to the existing settings panel, near the Ollama configuration:

- **Desired retention** — slider, 0.70 to 0.97, default 0.90. Label it in plain language: higher means shorter intervals and more reviews.
- **Maximum interval** — number input, default 36500 days.
- **Daily new item limit** — number input, default something small like 10.
- **Enable fuzz** — checkbox, default on.

Changing desired retention should recompute `due` for items already in `review` state, from their existing stability and `last_review`. Do not re-run the scheduler or touch stability — only the interval derivation changes.

Show a confirmation when this recompute affects a large number of items.

---

## Phase 7 — Inspector

Off by default. Toggle in settings, labelled as a developer or diagnostics view.

When on, render under the Drill item: stability, difficulty, retrievability as a percent, reps, lapses, state, and next due date. Compact, monospace, one row.

Optionally add the retrievability decay curve in the Learn view rather than Drill — it is a teaching visual, not a review-time one.

---

## Phase 8 — Later, not now

Do not build these in this pass. Record them.

- **Optimizer.** Once `review_logs` has a few hundred rows, run the FSRS optimizer over the history to produce personalized weights. Store them with a `params_version` and keep the defaults as a fallback.
- **Leech handling.** Items with lapses above a threshold get flagged and surfaced in a separate queue.
- **Per-topic retention.** Different desired retention for exam-critical topics.
- **Cross-subject scope.** Discrete and C++ share one queue with a subject filter.

---

## Order of work

Phases are sequential. Each has a verification step; do not start the next phase until the current one passes.

A reasonable commit boundary per phase:

1. audit notes
2. migration + schema
3. scheduler module + tests
4. rating derivation
5. home due strip
6. drill grade bar
7. settings
8. inspector

Bump the app version and cut a release only after Phase 6. Phases 7 and 8 can ride along in a patch.

---

## Definition of done

- A fresh install can complete a Drill session, close, reopen, and see correct due counts.
- An existing install migrates without losing any prior quiz history.
- Turning the feature flag off restores the previous home screen exactly.
- `review_logs` contains one row per graded item with no gaps.
- No file outside the scheduler module imports `ts-fsrs`.
