Report overhaul: per-topic accuracy broken down by study mode
--------------------------------------------------------------------------------
Date:     2026-08-11
Commit:   uncommitted
Files:    server/{schema.sql,db.js,index.js,stats.js},
          server/routes/{drill.js,stats.js},
          src/api/client.js, src/components/{ReportView,DrillView,ExamView,
          PracticeView}.jsx, src/components/ui/Select.jsx,
          src/components/report/StatsPanel.jsx, test/stats.test.js

Summary (plain-English version, written for a non-technical reader):

  THE PROBLEM
  The app can quiz you four different ways: a plain multiple-choice Quiz, a
  spaced-repetition Drill, a Practice session graded by a local AI model, and a
  timed Exam simulator. Until now the Report screen could not compare them. It
  showed one accuracy number per topic and that was it.

  That hides the thing you most need to know. Getting 100% on linked lists when
  the answers are listed in front of you is not the same as getting 56% when
  you have to write the answer from a blank page. Both are "linked lists", and
  the old report averaged them into one figure that flattered you.

  TWO THINGS HAD TO BE FIXED FIRST
  1. The app stored Quiz results and everything-else results in two separate
     places that were never designed to be read together. Nothing joined them.
  2. Drill and Practice were literally indistinguishable in the saved history.
     Both recorded themselves as "closed book", which is true of both, so there
     was no way after the fact to tell which screen an answer came from.

  Fixing (2) meant adding a new field recording which screen each answer came
  from. Answers saved before today do not have it and never can — the
  information was simply never written down. Rather than guess (and quietly put
  invented history in front of you), those older closed-book answers are left
  out of the Stats grid. New answers always land under Exam, Drill, Practice,
  or MCQ.

  WHAT YOU GET
  The Report screen now has two tabs. "Overview" is exactly what was there
  before, unchanged. "Stats" is new: two dropdowns — pick a topic, pick a mode —
  and the page reshapes itself to answer that exact question.

    - All topics + all modes  -> a grid comparing every topic against every mode
    - One topic + all modes   -> how you do on that topic in each mode
    - All topics + one mode   -> which topics are weakest in that mode, worst first
    - One topic + one mode    -> the detail, including your last 20 answers

  There is also a toggle between "first-try" (only the first time you saw each
  question, which is the honest predictor of an exam) and "all attempts", plus a
  30-day activity strip showing how much you actually studied.

  A NOTE ON HONESTY
  A getting-Hard-on-a-card counts as wrong here, the same as it does everywhere
  else in the app, so the two tabs can never disagree about the same answer.
  Where a number cannot be computed honestly the screen says so instead of
  showing something plausible: older quiz answers that predate per-question
  tracking are named and excluded from the first-try figure rather than silently
  dropped, and an empty slice says "no Practice attempts recorded for Linked
  Lists yet" rather than showing a grid of dashes.

  STILL TO COME
  Progress tracking and study streaks are each getting their own plan.

Summary (plain-English version, written for a non-technical reader):

  WHAT THE PROJECT IS
  SkillTape is a study app I built for myself and other students. You pick a
  course, pick a topic, and it drills you on that material — teaching cards to
  read, flashcards to flip, quizzes to answer, and full timed practice exams.
  Everything the app quizzes you on is written by hand from real course
  material, not generated on the fly, so the content is something a person can
  inspect, correct, and stand behind.

  THE PROBLEM THIS ROUND OF WORK SOLVED
  A study app is only as good as the answers it claims are correct. If one
  question has the wrong answer marked, the app doesn't just fail to help — it
  actively teaches the student something false, and the student has no way to
  know which question was the bad one. As the question bank grew past a
  thousand questions, "I'm fairly sure these are right" stopped being good
  enough. I needed a way to say, question by question, "a human has personally
  read this one and confirmed the answer is correct."

  WHAT I ACTUALLY DID

  1. Signed off on 93 questions, one at a time.
     In the previous release I built a review screen that shows unchecked
     questions one after another, like a stack of index cards, with a keyboard
     shortcut to approve or reject each one. This round I sat down and used it.
     93 questions across Big-O, container classes, C-style strings, inheritance,
     multidimensional arrays and recursion have now been read start to finish by
     a person and stamped as verified. The stamp lives on the question itself,
     so anyone reading the project can tell at a glance which questions have
     been through review and which are still waiting. This is the difference
     between "the content is probably fine" and "here is the audit trail."

  2. Added 55 new questions, in matched pairs.
     Every new question was written twice, in two different shapes:
       - a multiple-choice version, where you pick from four options; and
       - an open-ended version of the same question, where you get a blank box
         and have to produce the answer yourself, then compare it to a model
         answer and a checklist of the points you needed to hit.
     The reason is a well-established one in learning research: recognizing the
     right answer in a lineup is a much easier task than producing it from
     nothing, and it makes people feel more prepared than they are. Pairing the
     two means the app can quiz you the easy way while you're still learning
     the material, then quiz you the hard way — the way an actual exam will —
     once you think you know it. The same underlying idea, two levels of
     difficulty, no extra material to write later.

  3. Rebuilt two of the weaker topics.
     Recursion (27 new questions) and multidimensional arrays (16 new
     questions) were the two thinnest topics in the course and, not
     coincidentally, two of the ones students lose the most points on. Both
     were expanded into full practice banks. The new questions deliberately
     target the specific traps that show up on exams — for example, loops that
     fill a grid in an unexpected order because two counters were swapped, or
     code that prints a memory address when the student expects a number.
     Trees, stacks, queues, iterators, linked lists and inheritance each gained
     a pair of questions aimed at a known weak spot as well.

  4. Rebalanced how a practice session is built.
     The app assembles each session from a target recipe — so much recall, so
     much writing code, so much tracing through code, and so on. That recipe
     was written when the bank had very few multiple-choice questions in it.
     Now that the paired questions above exist, multiple choice is a bigger and
     more useful slice of a session, so the published recipe was updated to
     match reality: multiple choice went from a hard cap of 5% up to 25%, and
     the smaller specialist categories were trimmed to make room. The
     documentation and the app now describe the same thing, which matters
     because that recipe is the project's public claim about how it teaches.

  5. Removed an outdated rule that was still written down in six places.
     An early design rule said multiple choice could never be more than 5% of
     the material. That rule was abandoned back in August, and the app itself
     stopped following it then — but the sentence describing it was still
     sitting in the project's README, its planning document, its authoring
     instructions, and three code comments, quietly telling anyone who read
     them something that wasn't true any more. All six were rewritten to
     describe what the app actually does, with the one historical mention that
     remains explicitly labelled as dead so nobody reinstates it by accident.
     Stale documentation is worse than missing documentation: it looks
     authoritative and it is wrong.

  6. Small cleanup on the practice exam.
     The practice exam is 20 questions in 50 minutes. Those two numbers used to
     be typed directly into the middle of the code; they are now named settings
     at the top of the file, with a written note explaining how the exam
     behaves if you ask for more questions than the bank can supply. Nothing
     changed for the user — this is the kind of tidying that makes the next
     change to that screen cheap instead of risky.

  WHY IT MATTERS
  The theme across all five items is trust. A student using SkillTape is
  handing over their study time and betting the app is right. Verification
  stamps, hand-written and human-checked content, matched question formats that
  don't let you fool yourself, and documentation that matches the code are all
  ways of earning that bet rather than assuming it.

Summary:
  - Item bank: added WRITE items until every code segment in the stacks,
    queues, iterators, doubly-linked-list and templates decks had one. Stacks
    went 1 WRITE -> 7 (array pop/peek, linked-list ctor/push/pop/peek), queues
    1 -> 5 (class declaration incl. nextIndex, ctor, pop, peek), iterators
    gained one item per operator (*, ->, prefix ++, postfix ++, ==, !=) plus
    the ConstIterator ctor, doubly linked lists gained outputForward/
    outputBackward/length/clear/copy/search and the List destructor, and
    templates gained the Pair class declaration.
  - Two sources/ gaps closed rather than papered over with invented citations:
    Deck 03.3's algorithm slides (output forward/backward, length, clear, copy,
    search) and Deck 04.2's ConstIterator constructor were never ingested, so
    the items citing them had nothing to point at. Both were transcribed into
    sources/ under new anchors, with a dated comment marking them as hand-
    transcribed, and the items re-pointed from provenance:null to EXTRACTED.
  - Three transcription bugs were corrected on the way in, since an `expected`
    answer teaches whatever it contains: copy() walked `head` instead of
    `source.head` (it clear()s first, so the loop would exit immediately and
    leave an empty list), outputBackward called getPrev() where the deck's
    DNode declares getPrevious(), and the lecture's List destructor reads
    cursor->getNext() AFTER deleteNode(cursor) has freed it. The destructor was
    left verbatim — it's what the slide shows and what an exam would mark — but
    the use-after-free is now an explicit grading criterion rather than a
    silent rewrite.
  - Session composition: WRITE is the most expensive format to answer (90-300s
    budgets, all self-graded free text), and the additions above made it easy
    for a 20-item deck to sample eight of them. applyWriteCap() in
    itemSchema.js — the one module both the client and server already import,
    so there is a single definition — caps a MIXED deck at
    MAX_WRITE_PER_SESSION (3) and returns a WRITE-ONLY deck untouched, on the
    grounds that asking for nothing but WRITE is a deliberate choice to sit
    down and write code.
  - "WRITE-only" is read off the deck itself, not off a format picker, which is
    what lets the same function serve the exam route (no picker exists there)
    and still behave correctly when topic/difficulty filters happen to leave
    only WRITE items.
  - Wired into exactly the two places a mixed deck is built:
    PracticeView.startPractice, where the cap runs BEFORE the slice so the
    session still fills to the requested length with other formats instead of
    coming back short; and GET /api/drill/exam, which always caps and now
    recomputes topicMeta.sampled so the exam report can't count items the cap
    removed. The FSRS due queue (GET /api/drill/queue) is deliberately NOT
    capped — dropping due WRITEs there would defer scheduled reviews rather
    than reduce work.
  - Practice's setup screen states the cap when it applies ("max 3 WRITE per
    session (N available) — deselect every other format to drill WRITE on its
    own") and the Start button counts the capped pool, so a shortened deck is
    never a surprise.
  - test/applyWriteCap.test.js covers both rules plus the boundaries (limit
    override, limit 0 still exempting a write-only deck, empty/non-array
    input). Suite: 85 passing.
